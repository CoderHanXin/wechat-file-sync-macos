# 状态迁移说明

更新日期：2026-11-19。当前候选使用 SQLite v4，尚未发布；下方保留 v1 至 v3 的历史迁移说明。真实旧版安装升级及安全范围授权流程留待 M6 实机验收。

## 数据位置与格式

当前 fork 使用独立标识 `io.github.coderhanxin.wechat-file-sync`，状态位于其沙盒容器 Application Support/WeChatFileSync/state.sqlite。原作者容器和历史 WeChatDownloadSync 路径不自动读取；用户已确认本机无原版安装，未执行实际配置迁移。M1 的数据库版本为 1，M2 的 `PRAGMA user_version` 为 2，包含共享根目录、独立账号、按账号划分的历史基线和同步记录，以及未完成配置操作。

应用启动或写入型配置命令先取得同一个 `sync.lock`，再打开数据库并按需迁移。修改账号前应停止后台，具体操作见 [用户指南](user-guide.md)。只读列表与 `--check` 不迁移旧格式；旧版本需由持锁的正常启动或配置命令完成升级。

## SQLite v1 升级到 v2

1. 校验旧库版本和完整性，读取旧状态与书签。
2. 使用 SQLite Backup API 创建同目录的 `state.v1-backup-<UUID>.sqlite`，权限为 `0600`，校验备份可读；备份失败则不修改旧表。
3. 在单个事务中创建共享根目录和一个稳定 UUID 的“原账号”，迁移基线、planned / linked / conflict 记录与授权，更新版本。失败时回滚，v1 仍可读取。
4. 所有旧目标保持相对原管理根目录的路径，原实体和微信链接原地保留，不批量搬进新文件夹。
5. 持久化一条归档目录准备操作。源与根目录授权有效后，按身份创建独立归档文件夹；原有记录继续使用旧位置，后续新文件才进入 `微信文件/原账号/`。未知同名目录会安全避让，列表显示实际位置。

归档目录准备使用数据库外的文件系统操作，不能靠 SQLite 回滚；因此先保存计划，再排他创建临时目录、保存身份、排他改名和最终注册。中断后按身份恢复。旧目录尚未准备时，不接纳新增文件，已有记录能维护时继续维护。

迁移本身不读取微信聊天数据库、不移动实际文件。源或根授权失效时需要重新授权原目录，不因路径相同而接受身份已变化的目录，也不重建空基线。

## 旧 JSON 导入

只有没有已提交根目录与账号时，才导入旧 `state.json` 及同时存在的 `source.bookmark`、`downloads.bookmark`。`downloads` / `downloadsIdentity` 旧字段映射到通用管理根目录，直接导入 v2 的“原账号”；状态和授权在一个事务中提交。

导入成功后保留 JSON 与旧书签原样，以 SQLite 为准，不再重放。旧书签都不存在时可导入状态，但同步前须重新授权；只存在一个书签、JSON 无法解析、数据库损坏、未知版本或外键关系异常时，报告错误并保留现场，不回退过期 JSON 或重建空库。

## 移除与备份边界

移除账号会清空当前账号及未完成操作中保存的源书签，保留文件、链接、基线和记录。未完成操作已经选定的避让目录、临时路径和身份也保留，防止恢复时退回旧位置；尚未注册的新账号可按操作 ID 移除，并保留原 UUID 与基线。之后必须显式恢复并重新授权，不从旧 JSON 或迁移备份自动恢复授权。

升级备份、旧 JSON 和旧书签文件是历史快照，可能仍包含旧授权信息。移除不是磁盘安全擦除；这些快照不作为运行中的授权来源，应按本地敏感配置妥善保存。M2 不删除旧快照，也不承诺清除 SQLite 空闲页或系统备份中的历史字节。

## 诊断与回退

`--list-accounts` 和 `--check` 使用只读连接，后台持锁时仍可读取。`--diagnose` 会在已授权目录创建临时文件，因此 M2 改为取得写入锁并要求停止后台；它不是只读检查。

旧数据库备份仅代表升级前状态。升级后同步、改名和删除不会写入该快照；不能把它或旧 JSON 直接覆盖最新数据库。回退程序前先停止同步，备份完整应用支持目录，再核对实际文件和来源关系。M1 不能读取 v2，不支持直接换回旧程序继续处理最新状态。

一致性备份应在停止应用后复制数据库及其可能存在的日志文件，或使用 SQLite 备份机制。运行中任意复制一个数据库文件不能代替一致性备份。

## 已验证与未覆盖

临时样本已覆盖 v1 各阶段与书签原样迁移、旧路径保留、新文件进入独立目录、迁移各检查点失败回滚和重复打开、备份权限、JSON 一次性导入，以及损坏与未知版本不回退。账号移除后不重放旧授权、未完成配置的显式重新授权也有回归。

这些结果不代替真实安全范围书签、实际安装替换和异常掉电测试。具体数量及构建结果见 [验收记录](validation-report.md)。


## M3：SQLite v2 到 v3

v3 保留 M2 账号、根目录、授权、基线和账号配置操作，新增 `entities`、`sources`、`content_operations`、`account_settings` 和 `content_issues`。实体和来源通过包含账号 ID 的复合外键关联；操作还需匹配来源所属实体，不能跨账号或误指另一实体。

升级前生成权限为 0600 的一致 `state.v2-backup-<UUID>.sqlite`。元数据转换在一个事务内进行，linked 记录转为实体与来源；仅相同账号、相同位置及身份且均为 linked 的记录可共享迁移实体，不按内容合并历史副本。planned 与 conflict 不混入已完成实体，保留各自恢复与冲突证据。planned 保留原临时名、快照及路径并登记兼容操作；conflict 保持冲突，不伪装成完成。

原文件位置、微信链接、账号暂停和移除状态均保持。迁移不读取文件内容、不设置旧文件权限；旧摘要和权限来源未知就保持未知。以后新建实体的只读默认开启，旧实体复用时保持权限。

`transfers` 表在 v3 中仍作为旧移动和新建实体的兼容文件操作日志使用；它不是完整实体或来源清单。`LegacyTransferStore` 限定每次只恢复一条移动，不推进其他任务；完成后提交 v3 关系并移除对应兼容记录。其他未完成账号目录注册也继续按原计划恢复。

v2 到 v3 在备份后、记录复制后及提交前注入失败均回滚到可读 v2；无效旧路径也拒绝升级。JSON / v1 按阶段升级，若前一阶段成功，后续失败保留已完成阶段，不重新导入过期授权。只读入口不升级；M1、M2 程序不能直接继续使用 v3 数据库。

操作期间的冗余临时内容只在身份、内容及来源关联均核对后清理。数据库提交失败、未知源占用或目标变化时保留记录；源身份和原接收摘要按生命周期保留。已移除账号的历史数据不会因升级自动恢复授权。

实际临时样本结果见 [验收记录](validation-report.md)，本轮没有迁移本机真实状态。

## M4：SQLite v3 到 v4

基于 `ce7d43c` 在 `codex/file-association-recovery` 已实现最小 v4。按 [简化方案](file-association-recovery-plan.md)，v4 只补来源原因、清理／恢复操作及必要重绑约束，不建设内容版本、完整绑定历史、持久化预览和清理系统。

迁移前生成 0600 的一致 v3 备份，单事务转换并检查外键及记录。保留所有账号、基线、授权、暂停／移除状态、实体、来源、权限、错误及 M3 在途操作，包括链接目标历史。原接收摘要保持原义，未知保持未知，不因旧记录无摘要阻止用户明确选择副本。旧版 missing 只按已有“程序因失联清理”语义迁移，detached 不猜测原因；实时范围和占用检查仍必需。

迁移不访问微信、不移动或改权限、不恢复链接；失败回滚到可读 v3。旧程序拒绝 v4，只读命令不升级；旧格式按已提交阶段继续，不重放旧授权。临时数据库迁移和失败回滚已验证，没有操作真实配置，详见验收记录。

## 设置调整：无需数据迁移

账号发现与两页设置继续使用 SQLite v4。新账号在既有 source_bookmark 字段保存父目录书签，旧精确 msg/file 书签继续有效；旧程序的精确目录校验会拒绝新父目录书签，不会据此扩大范围。没有批量重建书签、基线或账号，没有改名、搬动已有归档。界面从源路径显示完整账号目录名，历史 name 字段和 CLI 兼容行为保留。停止管理清除本账号书签，其他账号持有的父目录访问许可可能仍有效；恢复必须显式确认，详见 [C17](decisions/0005-account-discovery-settings.md)。
