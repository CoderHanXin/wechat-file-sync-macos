# 微信文件同步开发计划

更新日期：2026-11-18。M0 核心决策已确认，M1 核心重构与自动回归已实现；实际验证见 [验收记录](validation-report.md)。需求依据见 [需求与行为规则](requirements.md)，设计依据见 [架构方案](architecture.md)。

建议继续在当前 fork 渐进重构，先完成文件处理正确性和可恢复性，再加入多账号、去重与界面。阶段以交付物和验收条件安排，不在范围未确定时承诺日历工期。

## 开发阶段

| 阶段 | 工作内容 | 交付物 | 完成条件 |
| --- | --- | --- | --- |
| M0 需求与方案确定 | 已确认去重范围、可配置管理根目录、恢复、只读、生命周期和 SQLite。其余细节随对应阶段细化。 | 更新需求、架构、测试计划；记录关键决定。 | 核心决定已有记录；未来界面和迁移细节不阻塞 M1。 |
| M1 核心重构与恢复 | 拆出文件操作、授权、存储和单账号引擎；补齐回归场景；隔离单文件错误；合并重复目录索引。 | 模块代码、独立自动测试、阶段验证记录。 | 保持原有正常行为；目标改名与旧名复用不误关联；源链接丢失或被替换不阻塞其他文件；失败后可恢复。 |
| M2 多账号与配置提交 | 添加稳定账号身份、独立授权、基线与目标目录，统一调度、暂停恢复及添加移除；保护配置提交。 | 多账号数据结构、配置操作入口、格式迁移方案。 | 两个账号的同名文件分目录保存；重复绑定被识别；账号失败不影响其他账号；添加失败不破坏已有配置。 |
| M3 去重与只读保护 | 实体与来源分离，计算内容摘要，实现多来源共享、权限设置、外部修改后索引失效，完善操作恢复。 | 去重与权限代码、关键决定记录、使用说明初稿。 | 相同内容仅展示一份；同名不同内容均保留；每条来源关联正确；重复实体合并中断不丢内容；可关闭只读保护。 |
| M4 删除与关联恢复 | 按确定规则区分正常可访问、失联和已删除状态，保留恢复记录，提供重新定位与重建关联能力。 | 恢复服务与基础入口、恢复测试、数据保留说明。 | 删除共享实体影响全部对应链接；恢复不覆盖源路径现有文件；微信源路径清理不反删归档内容；不隐藏保留完整副本。 |
| M5 原生配置界面 | 菜单栏、账号列表、添加移除、暂停恢复、重新授权、只读设置、真实错误状态与恢复入口。 | 可日常配置的应用、界面说明、用户指南。 | 配置不依赖重新安装；界面响应正常；进程存活与同步状态分开；不提供创建可编辑副本。 |
| M6 部署与真实环境验收 | 实现确定的登录启动方案、升级与旧服务处理、打包，执行真实微信与沙盒验证，整理发布说明。 | 安装升级文档、迁移文档、验收报告、发行包及校验文件。 | 安装、重启、退出、替换升级与卸载符合规定；同账号不被新旧服务重复处理；真实微信验证通过后再发布使用范围声明。 |

M1 的拆分过程中应为实体与多来源模型预留边界，避免先把一源一目标模式固化为公共接口。M3 和 M4 是同一套数据模型上的连续工作，M4 完成前不把去重版本作为可日常依赖的版本发布。

## 实施原则

- 每阶段形成可检查的改动；后续功能开发使用独立分支，文档整理提交保持范围清晰，不混入程序功能变更。
- 文件系统操作与状态提交一起设计恢复点，特别覆盖去重时移除冗余内容的过程。
- 自动测试使用隔离临时目录；真实微信验证单独安排，确认测试账号与允许操作的目录。
- 先核对内容，再建立共享关系；用户修改后的实体不能继续以旧内容摘要参与去重。
- 保留许可证及原作者声明，明确 fork 后的应用名称、应用标识和服务标识。
- 文档中的计划、测试状态和实际发布能力保持一致。

## 风险与处理

| 风险 | 处理方式 |
| --- | --- |
| 去重把多份源文件合为一个删除与编辑单元 | 在需求和设置中说明多条关联，明确删除与外部编辑规则。 |
| 普通只读无法完全阻止文件替换 | 将其定位为防误改，检测实际内容变化，不承诺强制另存或不可变归档。 |
| 稳定时间无法证明下载完成 | 对暂停续传和重新打开进行真实验证，保守等待，准确说明适用范围。 |
| 删除与移出范围无法仅靠路径消失区分 | 保留失联记录和重新定位途径，不以消失作为清除全部恢复信息的依据。 |
| 多账号扩大授权与配置失配风险 | 独立授权，先验证再提交，失败影响限制在当前账号。 |
| 源链接丢失等低频异常阻塞全局 | 建立逐文件、逐账号隔离；不假定微信一定会自动清理链接。 |
| 旧版本仍在运行 | 升级前识别并停用，保持同账号单一处理者。 |
| 未加入付费开发者计划 | 先完成本机 ad-hoc 构建和验证；正式分发签名与公证后续安排。 |
