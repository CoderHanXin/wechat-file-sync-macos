# 简洁性审视：M1 至 M6

日期：2026-11-19。代码基线：M3 `ce7d43c`；规划分支：`codex/file-association-recovery`。本轮只审视范围与机制并更新文档，不改代码，不重复功能测试；不替代 M1 至 M3 的正确性复核或真实环境验收。

产品方向已确认：专注本机微信文件归档、同账号去重和链接维护，功能单一可以接受。下面区分现有实现、已经确认的 M4 收缩，以及对后续阶段的建议；建议不自动取消既有决定。

## 结论

M1 至 M3 未见需要为“简化”而立即推倒的通用框架。当前核心使用系统 SQLite、串行调度与有界内容读取，没有引入插件系统、服务拆分或云端依赖。主要复杂度来自会移动和删除内容、改变权限的文件操作；删除这些保护会增加丢文件和误关联风险。

确实需要控制的范围是：M1/M2/M3 的兼容层长期叠加、面向用户的诊断／恢复入口数量，以及把恢复功能扩展成历史版本和审计系统。M4 已按用户决定收缩；其他已验证代码暂时保留，不为减少文件数重构一遍。

## M1：核心拆分与可靠性

| 项目 | 判断与处理 |
| --- | --- |
| 文件身份、范围检查、源路径复用检测 | 保留。只靠文件名会误关联，属于核心正确性。 |
| SQLite、事务、进程写锁与文件操作日志 | 保留。多来源状态要一致，数据库事务无法回滚已发生的文件移动。 |
| 单文件错误隔离及共享根目录索引 | 保留。避免一个异常阻塞全部同步、每条来源重复全目录查找。 |
| 模块划分及故障注入测试接口 | 目前可接受；不按模块数量判断复杂，不另加通用仓库／事件总线。 |
| 单账号旧状态与 JSON 导入 | 已实现并有迁移测试；不扩大为持续双写或任意旧版恢复框架。 |

依据：[文件系统操作](../Sources/Core/FileSystem.swift)、[旧移动引擎](../Sources/Core/SyncWorker.swift)、[进程锁](../Sources/Core/ProcessLock.swift)、[根目录索引](../Sources/Core/ManagedRootIndex.swift)。

## M2：多账号

多账号和按账号归档是明确需求，不属于范围膨胀。稳定账号 ID、独立授权与基线、暂停只停新增、移除后不删文件，均保留。

账号目录准备的操作日志比普通配置保存复杂，但它处理的是已经创建或改名的实际目录，不能只靠数据库事务；现阶段不重写。账号恢复和重新授权已确认，不以简洁为由擅自删除，只建议从正常操作界面中收起低频诊断入口。

现有多账号调度采用串行执行，适合当前规模。不要再加多进程 worker、多个后台服务、可配置并发池或多账号调度策略。

依据：[账号管理](../Sources/Core/AccountManager.swift)、[账号配置入口](../Sources/App/Directories.swift)、[当前调度](../Sources/Core/ContentCoordinator.swift)。

## M3：去重与只读

| 项目 | 判断与处理 |
| --- | --- |
| 实体与多来源分开 | 必需。否则无法表达同一内容的多个微信入口和共享删除影响。 |
| 摘要、复用前字节比较、交换与回滚 | 保留。去重会实际移除冗余字节，不能按名字或旧缓存盲删。 |
| 扩展属性／ACL／硬链接边界 | 保留现有拒绝不安全情况的检查，不扩展为元数据合并和修复工具。 |
| 只读默认值与已存在文件显式应用 | 已确认且已实现，保留。界面以未来新文件的一个开关为主，批量改旧文件放低频入口。 |
| 本工具移除写位的记录 | 保留，避免解除只读时把用户原有权限改坏。 |
| 分块读取和有限摘要预算 | 适量资源控制，保留内部常量；不做用户调参面板或严格公平调度框架。 |
| 外部编辑检测 | 只失效摘要、重新核对与报告，不保存内容版本，不增加版本比较或原件库。 |

依据：[内容读取](../Sources/Core/ContentFingerprint.swift)、[去重接纳](../Sources/Core/ContentWorker.swift)、[交换与清理](../Sources/Core/ContentOperationRunner.swift)、[权限处理](../Sources/Core/ReadOnlyPolicy.swift)。

现有一个具体使用限制需要如实说明：当同内容候选的附加属性不兼容时，程序可能保留源文件并报告，而不是完成归档。这是当前保守边界，不应为追求“兼容所有文件”新增属性合并设置。若真实使用频繁遇到，再单独讨论“不去重但正常归档”的小范围回退方案；本轮不改变行为。

## 已有实现的维护负担

当前生产入口使用 `ContentRepository` / `ContentCoordinator`，但新建实体仍通过 `LegacyTransferStore` 复用 `SyncWorker`，同时保留 v3 内容操作与 `transfers` 移动记录。这减少了重写已验证移动逻辑，却形成了双模型适配。

`SyncCoordinator` 等旧路径也仍被旧回归和自测调用。它们不是简单的无引用死代码，不能现在直接删除。建议后续只有在修改该区域、并能明确减少一套维护路径时，再把实际移动原语抽出，统一到当前引擎；旧迁移读取代码仍保留。不为“架构统一”另开一轮大重构，不给 M4 增加前置工程。

依据：[生产入口](../Sources/App/main.swift)、[兼容适配](../Sources/Core/LegacyTransferStore.swift)、[当前移动恢复](../Sources/Core/ContentWorker.swift)、[自测](../Sources/App/SelfTest.swift)。

当前命令将账号、文件问题、授权检查和在途恢复分别暴露给用户，开发阶段有用，日常使用成本偏高。建议保留其实现作为诊断工具，M5 收敛正常入口为账号列表、归档目录、只读开关及必要恢复，不为每条 CLI 建一个按钮或一个页面。

## M4：本轮已确认的收缩

- 原身份返回自动恢复程序清理的链接；不同身份副本由用户指定并预览确认。
- 保留原名、路径、账号、来源、现有可得摘要及清理原因。不建设完整内容版本、历次绑定和审计事件系统。
- 摘要只帮助判断；缺摘要或不一致时明确告知，由用户决定关联内容，不做历史原件鉴定。
- 复用同一逐来源执行逻辑和必要操作日志；不把预览设计成长期持久化计划、审批或任务管理系统。
- 历史清理暂缓，不增加到期设置、清理计划和专用界面。

范围检查、不覆盖源占用、账号隔离、保护原权限及中断可重试继续保留。具体实施与临时样本场景以 [M4 方案](file-association-recovery-plan.md) 为准。

## M5 与 M6：建议保持的最小产品

| 阶段 | 保留的目标 | 建议暂不扩展 |
| --- | --- | --- |
| M5 | 菜单栏状态；一个设置窗口，包含账号、管理目录、暂停／恢复、必要授权、只读默认和关联恢复。关闭窗口继续运行，退出停止。 | 文件浏览器、统计仪表盘、逐实体管理中心、版本历史、复杂规则、资源参数、后台任务面板。 |
| M5 目录设置 | 新用户可选择自定义根目录，已有根目录可重新授权，下载不是硬编码。 | 已有归档一键跨盘迁移、自动搬目录。原计划的根目录更换流程建议单独细化，首版不把它变成隐式搬家功能。 |
| M6 | 一个明确的安装方式、一种实际采用的登录启动方案、升级保留状态和停用旧服务、卸载说明、真实微信及授权验收。 | 同时维护多套安装渠道、并行运行新旧服务、自动更新器、额外常驻守护进程、自定义证书管理界面。 |

以上是范围建议，不是在本轮实现或改变已确认的账号／生命周期行为。根目录更换若只是重新选择路径，也不能跳过身份和既有归档处理；暂缓跨盘搬运与保留“可自定义初始根目录”并不冲突。

先做最小可用设置界面和必要真实验收，得到实际反馈，再决定是否补低频功能。真实微信验收、签名沙盒、安装升级以及已声明系统／架构的验证不能因“功能少”而省略；本轮继续不操作真实微信。

## 后续工作准则

每次新增功能先说明它解决哪一个已经出现或明确提出的问题；能用一个默认行为解决，就不增加设置。只有影响正确性或明显使用负担时才增加抽象、缓存和后台任务。

测试围绕文件是否保留、链接是否正确、权限是否越界和重启能否继续，不为了数量或逐函数覆盖增加镜像测试。文档以需求、当前架构、使用说明和实际验收为主；阶段方案在实现后记录差异，不再为每个小参数增加一份决定文档。

本轮只调整 M4 已确认范围，并把以上建议记录为后续约束参考；没有删改 M1 至 M3 代码或旧测试，没有重新宣称其通过。下一步应按精简 M4 的 S1 开始最小数据迁移，随后完成两条恢复路径，不把兼容层整理和新 GUI 提前混入。
