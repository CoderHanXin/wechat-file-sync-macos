# 内容去重与只读保护决定

日期：2026-11-18。实现基线：M2 提交 `4951d59`。M3 分支：`codex/content-dedup-readonly`。

以下三项已于方案阶段由用户逐项确认，作为本轮实现依据。程序已在当前分支接入 v3，未操作本机真实配置或微信文件；其他实施建议见 [M3 实施方案](../content-dedup-readonly-plan.md)，不得把建议写成已确认或已实现。

2026-11-19 补充：文中提及的 M4 恢复与期限细化，现以 [M4 简化决定](0004-file-association-recovery.md) 为准；历史清理已暂缓，M3 实现和验收结论不变。

## C07 只对后续新接收文件执行合并

升级时保留已有归档的位置、名称及重复副本，不自动批量合并或删除历史实体。已有受管理的归档经重新校验后，可供后续新接收的同账号文件复用。

“历史归档”指 M2 已管理的实体，不包含启用前的微信历史基线，也不包含用户放入管理根目录的其他文件。本阶段不增加历史文件批量去重入口。

## C08 相同内容不因名称或扩展名不同而拆分

在同一账号内，支持范围内的文件内容字节完全相同时合并，保留最先选定实体的当前名称和位置，记录每条微信来源的原名、扩展名和原相对路径。不因为新来源使用其他名称而改名已有实体，也不另建一个归档别名文件。

相同名称但内容不同的文件分别保存；不同账号仍独立保存。扩展名不同的真实微信预览、打开和默认应用兼容性留待真实环境验收，临时样本测试不能代替该结果。

## C09 只读设置作用于以后新建的实体

只读默认开启。设置变更作用于之后创建的实体；已有实体的权限不随开关自动改变。

新来源复用已有可写实体时保留其权限，不为了接纳这一来源而自动保护旧实体。新来源复用已有只读实体时同样保留权限。需要统一保护或调整已有实体时，另行显式应用并报告结果。

因此“新增来源”和“新建实体”必须在设置说明和状态中分清：一个新接收文件复用旧实体，并不代表它现在受只读保护；实际保护状态以实体权限为准。

## 既有决定继续生效

- 去重范围限定于同一账号；同一实体可关联多条微信来源，来源属于原账号，不随整理位置变化。
- 使用可配置管理根目录；下载目录只是默认建议。
- 普通只读用于防误改，不承诺所有应用强制另存，不提供不可变原件或隐藏备份。
- 不提供创建可编辑副本、文件编辑或版本管理功能。
- 删除共享实体允许全部关联失效；微信侧清理不反向删除实体。保留必要来源记录，手动恢复与期限策略在 M4 细化。
- 修改配置前停止后台；暂停只停止新增接纳，已有持久化操作继续恢复。移除账号清除当前源授权，停止访问与管理，不自动从备份取回授权。
- 使用 SQLite、单写入通道和版本化迁移；文件操作需独立持久化恢复阶段。
- 测试只用临时样本、假授权和命令替身，不操作真实微信文件、真实应用配置或登录项。
