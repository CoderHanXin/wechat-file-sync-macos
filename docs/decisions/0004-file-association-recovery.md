# 删除与关联恢复决定

日期：2026-11-19。基线：M3 提交 `ce7d43c`；分支：`codex/file-association-recovery`。状态：简化方案已由用户确认，核心与 CLI 已实现，尚未发布。本记录取代本轮早期“所有旧关联都只显式恢复”及“历史清理纳入 M4”的方案。

## C10 原文件身份返回自动恢复，副本手动指定（已确认）

原文件回到当前管理根目录，且设备、inode、创建时间等身份符合既有记录时，自动恢复此前由本程序因该实体失联而清理的链接。不要求用户重新选文件，也不要求内容仍与接收时一致；外部编辑仍按 M3 规则失效去重缓存，不覆盖内容。

只有内容相同但身份不同的新接收文件，不属于“原文件返回”。正常接纳新文件，不凭摘要相同自动激活旧关联。用户找到的是另一份副本时，自行指定并在预览后确认恢复。

自动恢复只针对有本程序清理记录的来源；微信侧自行清理、原因未知、源路径被新生命周期使用的来源不自动重建。任何恢复均不覆盖现有未知对象，不重建微信父目录，不跨账号共享。

## C11 保留必要记录，历史清理暂缓（已确认）

必要元数据默认长期保留，不自动过期。历史记录清理不纳入 M4，也不预先承诺在 M5 实现；有实际需求后再讨论。暂不增加清理计划、到期设置、清理界面及配套标记系统。不保存隐藏文件内容副本。

## C12 候选先自行放回当前管理根目录（已确认）

另一份副本位于根目录外时，用户先自行放回当前管理根目录，再指定并恢复。M4 不新增导入、搬运或复制流程。管理根目录由用户配置，下载目录只是默认建议。

## C13 手动指定重在明确告知，不鉴定历史原件（已确认）

用户指定文件后，展示账号、原名、最后归档位置、已知大小、拟恢复来源，以及候选路径、大小和摘要核对结果。已有可靠摘要可辅助判断；缺少摘要显示“无法核对原内容”，不因此禁止用户确认。摘要不一致时明确提示将改为关联用户选择的内容，再由用户确认；不另设隐藏的“强制信任”模式或历史证据门槛。

可选择恢复来源，执行前展示成功候选、跳过项及原因。用户确认不能绕过源路径占用、授权范围、账号隔离、在途操作或目标变化检查。程序不读取聊天数据库，不显示并不掌握的联系人、群聊或接收时间，也不保证恢复微信历史消息。

## C14 简洁优先（已确认的产品方向）

软件专注于本机微信文件归档、同账号去重与本地链接维护。功能单一可以接受，默认行为应清楚；不为假设中的需求提前建立通用框架或复杂配置。

安全移动、内容删除前校验、权限边界、账号隔离、单写入锁及必要中断恢复继续保留。M4 不建设完整内容版本系统、绑定审计历史、持久化预览计划或元数据清理系统。SQLite 只增加落地功能必需的字段和操作类型；若需升级 v4，迁移本身仍须可靠。

测试继续仅使用临时样本、假授权和命令替身，不操作真实微信文件、真实应用配置或登录项。写入型命令沿用先停止后台、取得统一写锁的方式；M5 界面再在同一进程内串行处理。
