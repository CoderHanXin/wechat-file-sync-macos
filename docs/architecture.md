建议继续在当前 fork 分阶段重构。复用现有文件身份识别、同名保护、安全移动、符号链接、进程锁和书签处理实现，并结合新场景重新验证；重新组织账号、内容、多条来源和界面之间的关系。状态存储采用 SQLite，关键决定见 [M0 核心决策](decisions/0001-m0-core-decisions.md)。

## 模块职责

| 模块 | 职责 |
| --- | --- |
| 文件操作 | 不跟随链接地检查对象，验证目录边界，安全移动、改名与链接操作，设置权限。 |
| 目录授权 | 保存、解析和更新安全范围书签；报告授权与目录身份变化。 |
| 状态存储 | 统一保存配置、实体、来源与操作记录；管理事务和格式迁移。 |
| 单账号同步引擎 | 建立历史基线，发现候选文件，等待稳定，核对内容并执行同步。 |
| 多账号调度 | 管理账号启停、共享目录索引、隔离错误并限制并发文件操作。 |
| 应用界面 | 展示运行状态，接收配置与恢复操作，管理菜单栏和登录启动。 |

同步引擎在后台运行。界面通过统一任务入口发起操作；状态存储使用统一写入通道，避免界面、扫描和恢复任务同时修改同一条记录。

## 账号与目录

每个账号具有稳定的内部 ID、用户备注、源目录书签、源目录身份、目标相对目录、启用状态和历史基线。重复选择同一个源目录应识别为已有账号。

```text
<用户配置的管理根目录>/
└── 微信文件/
    ├── 个人微信/
    └── 工作微信/
```

目标文件夹名称需要处理重名、大小写及文件系统名称限制，不能通过拼接任意备注直接得到访问路径。目标目录应绑定身份；丢失或被其他目录替换时，暂停该账号并提示处理。

每个同步任务区分三个目录概念：微信源目录、账号初始归档目录、允许寻找移动文件的管理根目录。管理根目录可由用户设置，下载目录仅为默认值；核心、存储和路径检查使用通用目录模型。M1 验证任意目录，M5 完成图形设置与授权。

## 内容与来源分开保存

现有记录主要是一条源路径对应一个目标。内容去重后，应分别记录实体和来源。

| 对象 | 建议保存的信息 |
| --- | --- |
| 实体文件 | 内部 ID、所属去重范围、内容摘要、字节数、当前相对路径、文件身份、权限策略、当前状态。 |
| 微信来源 | 内部 ID、账号 ID、源相对路径、接收时发现的文件身份、原始名称、首次发现时间、对应实体 ID、链接状态。 |
| 操作记录 | 操作 ID、涉及实体和来源、计划目标、当前阶段及恢复所需信息。 |
| 历史基线 | 启用该账号前已有文件的路径和身份，避免把历史文件当新接收内容处理。 |

同一实体可以关联多条来源。来源消失时不级联删除实体；实体删除时更新其全部来源。实际来源条数从记录中核对，不仅依赖容易漂移的计数。

首次发现时间不能标成微信消息发送时间。没有数据库集成时，不生成发送者或聊天来源信息。

## 内容去重流程

1. 候选文件稳定后，读取文件内容并计算流式摘要，建议使用 SHA-256，避免一次性将大文件载入内存。
2. 在读取前后核对文件身份、大小和修改时间；发生变化则推迟，重新观察。稳定阈值仍不能证明微信已经完成下载。
3. 在确定的去重范围中寻找大小和摘要匹配的实体，并确认实体仍存在、内容仍符合记录。M3 方案建议在复用前逐块进行字节复核，不仅凭缓存摘要合并。
4. 已有匹配实体时，先持久化来源接入计划，再安全地把新源路径转换成指向实体的链接。移除重复内容前必须保留足够的恢复信息并重新验证两端。
5. 没有匹配实体时，执行原有安全移动方案，记录新实体，再建立微信链接。
6. 操作完成后提交关联和状态。中断后重跑同一操作应得到一致结果，不重复创建实体，也不覆盖其他文件。

同名不同内容继续使用名称避让。后续新接收的同内容不同名称文件复用选定实体，其当前名称不变，各来源原名分别保留；不同扩展名同样按内容合并，真实打开兼容性另行验收。旧重复副本不自动批量合并，具体见 D02 和 C07、C08。去重过程中应保持与原版一致的本地文件范围，不访问网络识别内容。

## 只读保护与外部修改

只读施加于实际文件，所有微信链接共同指向该实体。权限变更保留原有其他必要权限，不用固定权限值覆盖原模式。操作阶段和恢复记录需要覆盖权限变更，防止下载未完成时提前施加限制。

只读设置默认开启，作用于以后新建实体；新增来源复用旧实体时不自动改权限，已有实体仅单独显式应用，见 C09。普通只读权限用于限制直接写入，不提供不可变性。父目录可写时，外部程序可能通过替换文件更新内容。关闭保护或手动解除保护后，也可能直接修改实体。

因此，文件内容索引必须能失效和重新校验：实体变化后不沿用旧摘要进行去重，不覆盖用户编辑，不把旧内容身份无条件转给新内容。具体状态与提示在 M3 细化。

本工具不提供创建可编辑副本。另存、复制和权限调整由用户通过外部工具完成。

## 删除与恢复

实体在管理范围内找不到时，先标记失联。当前程序无法仅凭目录中不存在区分删除、移出范围和临时不可访问，不能立即据此断言用户已永久删除内容。

确认不再维护微信访问后，移除仍指向该实体的微信链接，保留必要的实体及来源记录。不删除已经出现在源路径的其他普通文件或用户建立的其他对象。

M4 规划：原文件身份回到管理根目录时，自动恢复本程序因失联清理的链接；不同身份副本由用户指定并预览确认，已有摘要用于辅助告知，不作为缺证据即禁止恢复的门槛。重建链接前检查父目录存在、源路径未被其他文件占用，并在账号授权范围内执行。原消息或原父目录已被清理时，不默认重建整个微信目录结构。

保留的关联记录不能恢复文件字节。不隐藏保存已删除文件的完整副本。移出范围保留失联记录；必要元数据长期保留，历史清理暂缓。微信侧自行清理或旧路径被新生命周期复用，不自动复活。

## 状态提交与中断恢复

采用系统 SQLite，通过统一的状态存储接口和事务提交数据。M1 使用单账号表结构，M2 已迁移到按账号隔离的 v2；实体和多来源关系留待 M3。旧 JSON 成功导入后保留，已有数据库损坏时不自动回退旧状态或重建空库。存储需要覆盖多来源到一实体、删除记录、索引失效和配置升级。

添加账号时先验证授权、目录、重复绑定和目标冲突，准备初始基线及状态，再将账号注册为可运行任务。失败或中断不得覆盖其他账号的有效书签和状态。数据库事务不能直接回滚文件系统操作，仍需记录文件操作阶段并按实际两端状态恢复。

每条来源处理独立捕获错误；某一账号不可用时只暂停该账号。持久化失败、磁盘空间不足和目录暂时不可用应保留可诊断状态，不自动重建空状态继续操作。

## 性能与调度

建议每轮按需构建一次管理目录的文件身份索引，由多个来源及账号复用。文件内容摘要仅在首次处理或失效后重新计算；避免每两秒对所有归档文件重新计算。

控制大文件计算与移动的并发，避免影响微信下载和桌面响应。合并普通状态更新；影响文件删除或移动安全的操作计划应在执行前持久化，不能为了减少写盘省略恢复记录。

## 应用生命周期与部署

已确定采用原生菜单栏与同步引擎同进程，关闭配置窗口继续运行，退出应用停止同步。当前 M5／M6 已实现该生命周期及显式登录启动，新的安装流程不创建 KeepAlive；旧脚本只作为历史机制说明。登录启动不保证崩溃自动重启。

macOS 13 及以上可以使用 SMAppService 管理登录项或内置 LaunchAgent。迁移时清理或停用旧服务，保证同一账号只有一个有效处理者。应用和服务使用本项目确定的标识，避免与原版安装冲突。

本机构建阶段沿用 ad-hoc 临时签名，不以付费开发者会员作为开发前置条件。现有脚本可使用 Command Line Tools；引入 Xcode 工程构建时再将完整 Xcode 列为该构建路线的依赖。正式分发签名、公证与证书管理单列在发布计划中。

参考：[SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice)、[mainApp](https://developer.apple.com/documentation/servicemanagement/smappservice/mainapp)、[命令行工具](https://developer.apple.com/documentation/xcode/installing-the-command-line-tools)、[应用公证](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)。

M1 数据库包含 `configuration`、`baseline`、`transfers`、`bookmarks` 四张单账号表，使用 `PRAGMA user_version = 1`。身份和观察快照以结构化编码保存在 BLOB 字段；来源关系仍是一源一目标的过渡实现，M2 已加入多账号，多实体共享留待 M3。v1 类只用于旧格式校验、迁移及旧回归夹具；应用不再用它保存当前配置。

每次状态提交仅更新发生变化的基线与同步记录，不重写整个 JSON。安全移动前先持久化 planned 阶段，链接完成后提交 linked；普通批量关联清理合并提交。状态保存失败会停止当前扫描，待下一轮先补齐持久化后再操作文件。

文件移动后若目标身份不符，保留冲突而不把未知目标回退到微信源目录。planned 阶段恢复时，若原目标已改名，则在管理根目录按原身份寻找，先持久化新的计划路径，再在下一轮完成链接。

目标身份改变时先在管理根目录寻找原身份，找不到则进入冲突状态，保留文件而不自动接管替换内容。已存在的冲突记录需在后续恢复功能中处理。M1、M2 仍沿用失联后移除旧链接与活动记录的行为。M3 已保留最小实体与来源失联记录；M4 按后文简化方案补充两条恢复路径，记录清理暂缓。

## M2 实现位置与提交边界

| 实现 | 文件 |
| --- | --- |
| 账号 UUID、目录身份与配置操作模型 | `Sources/Core/Accounts.swift` |
| SQLite 连接、参数绑定、事务及一致备份 | `Sources/Core/SQLiteConnection.swift` |
| v2 表、迁移、配置仓库与账号限定存储 | `Sources/Core/AccountRepository.swift` |
| 账号校验、目录注册恢复、暂停、备注和重新授权 | `Sources/Core/AccountManager.swift` |
| 串行调度、逐账号授权租约和错误隔离 | `Sources/Core/SyncCoordinator.swift` |
| 同轮共享的惰性身份索引 | `Sources/Core/ManagedRootIndex.swift` |
| 严格解析账号命令，未知参数报错 | `Sources/Core/Command.swift` |

v2 使用 `managed_roots`、`accounts`、`baseline`、`transfers`、`account_operations` 五张表。基线与记录的主键为 `(account_id, relative)`，外键不级联清除；源身份的唯一键由设备、inode、创建时间字段构成，不依赖 BLOB 的 JSON 字节顺序。账号内的 worker 快照仍沿用 `SyncState.version = 1` 结构，这不是数据库版本。

一个 `AccountRepository` 连接由所有 `AccountStateStore` 共享，适配器保存只更新本账号记录，不改授权、备注或暂停意图。配置入口和后台都先取得进程写入锁；列表、检查以只读连接读取且不迁移。M2 不支持后台运行中修改配置。

`AccountManager` 先保存含基线的操作计划，再准备独占临时目录并记录身份，排他改名后在事务中注册账号并清除计划。失败保留计划及目录；没有可靠身份的目录不自动接管或删除。迁移账号已有记录，目录准备完成时只更新归档绑定，不重放基线或覆盖同步记录。恢复以当前持久化计划为准，完成后的旧计划重放不再创建目录；账号移除只清除计划的授权并标记停用，保留操作已经确定的目标与身份。未完成新增账号也可移除并保留原基线，显式恢复后继续原操作。

`SyncWorker` 先维护已有记录与 planned 操作，再根据账号开关及归档身份接纳新文件；所有初次选址和重名重试都保存根目录相对路径。`SyncCoordinator` 串行调度，各账号分别获取、释放源访问租约。根目录授权在后台运行期间持有，每轮复核根身份；源故障仅影响当前账号，持久化失败停止整轮并退出后台。

共享 `ManagedRootIndex` 每轮按需枚举一次，缓存成功和失败结果，返回前再次核对实体身份；本程序移动实体后增量登记。下一轮重建，账号归属不随用户的整理位置变化。配置列表只显示用户意图和保存位置，授权的即时检查由 `--check` 完成，后台错误写入日志，该阶段尚无设置窗口，M5 的当前入口见下文。


## M3 实现与恢复边界

| 实现 | 文件 |
| --- | --- |
| 实体、来源生命周期、操作类型和阶段 | `Sources/Core/ContentModels.swift` |
| v3 迁移、复合关系约束、设置和持久化错误 | `Sources/Core/ContentRepository.swift` |
| 不跟随链接的描述符读取、分块摘要、字节比较和元数据核对 | `Sources/Core/ContentFingerprint.swift` |
| 按账号候选接纳、实体与多来源核对 | `Sources/Core/ContentWorker.swift` |
| 来源交换、关联提交、冗余清理与回滚 | `Sources/Core/ContentOperationRunner.swift` |
| 逐实体权限日志及原写位恢复 | `Sources/Core/ReadOnlyPolicy.swift` |
| 限定单条旧移动的兼容存储 | `Sources/Core/LegacyTransferStore.swift` |
| v3 调度、命令解析和应用入口 | `Sources/Core/ContentCoordinator.swift`、`Sources/App/ContentCommands.swift` 与 `main.swift` |

v3 在 M2 表上新增实体、来源、内容操作、设置及错误表。实体不以摘要作为唯一键，历史副本保留；来源到实体、操作到所属来源与实体均带账号约束。源路径复用生成新生命周期，原接收摘要与当前实体摘要分开。JSON 使用稳定键顺序编码，内容未变化的 UPSERT 不写入相同记录，空闲轮次不重写状态。

新建实体复用经回归的移动引擎，但每次通过 `LegacyTransferStore` 只加载、保存一条移动，完成后转入 v3 关系；这也是 v2 planned 的兼容恢复路径。默认只读任务在移动后、安装最终微信链接前完成，权限失败保留计划和归档内容，其他任务仍可继续。

去重接入在创建或更新链接前先记录目标历史，回滚只识别日志中的链接。描述符验证同时复核授权根身份和父目录边界，清理及权限变更前后再次核对。去重接入使用交换保留原重复内容；关联与 cleanup 阶段先提交，再清理身份与内容均确认的临时文件。清理后提交失败可幂等完成；清理前实体丢失或不一致时持久化回滚并恢复源内容。未知源占用或临时内容身份不符时不盲删，错误写入 `content_issues` 及操作，供只读诊断查看。

原权限、实际权限、未来新实体默认值分别记录。只恢复本工具明确移除的写位，不自动解除用户原有只读；ACL、不可变标记或其他硬链接不安全时保留文件并报告。扩展属性合并要求兼容，元数据校验有大小上限，不降级隔离属性。

观察摘要每账号每轮默认预算 4 MiB，同时最多保留一个跨轮摘要任务和必要租约；暂停或移除时释放未接纳任务。候选摘要缓存带身份、尺寸、mtime、ctime、模式等快照；相同内容候选在复用前仍重新读取并逐块比较。目标最终校验及不可逆操作前复核按单文件完成，尚不提供整个大文件处理的严格时间抢占。

M3 自动维护共享实体位置和来源，失联后保留记录并清理仍属于本工具的链接；首次清理失败会对仍有活动来源的失联实体继续重试，冲突来源不被普通扫描自动接管；不隐藏保留完整原件、不提供手动重新定位或恢复旧链接。真实微信、不同扩展名默认应用选择和签名沙盒升级仍待 M6 验收。

## M4 实现：最小数据与两条恢复路径

基于 M3 `ce7d43c` 在 `codex/file-association-recovery` 规划。以 [简化方案](file-association-recovery-plan.md) 和 [C10 至 C14 已确认决定](decisions/0004-file-association-recovery.md) 为准，取代早期完整内容证据／绑定历史／清理计划设计。

拟升级 v4，仅补来源结束原因、清理／恢复操作类型及必要重绑。已有身份和来源生命周期继续使用；摘要用于去重或手动恢复辅助告知，未知不补造。不同物理身份不改写旧实体身份或继承旧权限所有权。相关在途操作先结束，再事务更新当前关联。不建立完整版本表、绑定审计或独立的持久化预览计划。

程序清理失联链接前保存操作意图；原身份返回时只恢复这些可核对来源。另一副本由用户选择，展示原记录、候选和影响后确认。两条路径复用逐来源执行日志、排他安装及范围复核，不覆盖未知对象；数据库失败停止后续动作。访问或枚举失败不判作删除。

纯记录列表不扫描或迁移，M4 手动写入命令要求先停止后台，M5 已通过同进程串行入口操作。候选保留名称、位置和权限，外部文件由用户移回，不跨账号共享。记录清理暂缓。M1 至 M3 维护负担与后续范围建议见 [简洁性审视](simplicity-review.md)。

## M5 / M6 当前实现

`ApplicationSession` 持有统一状态连接、进程锁和当前协调器；`DesktopWorker` 在一个 utility 串行队列中扫描、提交配置和执行恢复，主线程只负责 AppKit 控件、授权选择与确认。单账号源错误继续隔离，数据库错误停止扫描。配置改变释放未接纳观察任务，持久化操作留待核对。

`DesktopController` 提供菜单栏和一个设置窗口，关闭窗口继续运行；退出回调等待队列结束当前动作并释放会话。不另加后台服务。原身份自动恢复与副本恢复都复用 M4 的 LinkRecovery，预览不持久化，源占用不覆盖。失联链接先排他移到已记录临时位置，核对实际对象再清理，替换内容不盲删。

独立标识为 `io.github.coderhanxin.wechat-file-sync`，配置位于对应沙盒容器的 Application Support/WeChatFileSync。构建目标仍为 macOS 13+；CLI 与 UI 共用连接规则和写锁，只有纯查询可与正在运行的应用并存。

登录启动由设置中的 `SMAppService.mainApp` 显式开关控制。安装脚本只复制应用、不配置、不注册服务；升级要求先退出，验证 staging 后替换，失败回滚；卸载注销登录启动后只移除应用，保留数据。细节和未覆盖真实流程见 [桌面与部署方案](desktop-app-plan.md)、[部署说明](deployment.md) 与 [验收记录](validation-report.md)。
