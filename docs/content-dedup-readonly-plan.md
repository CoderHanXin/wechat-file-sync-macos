# M3 内容去重与只读保护实施方案

日期：2026-11-18。基线：M2 提交 `4951d59`，已有本地回归基线为 86 项。分支：`codex/content-dedup-readonly`。状态：C07 至 C09 已确认，M3 核心、命令及临时样本回归已实现并完成提交前重点复核，尚未发布。

本文保留方案设计及确认依据，具体落实、差异和实际测试见末尾实现说明及验收记录；未覆盖项不记为通过。

## 已确认事项与范围

M0、M2 的决定继续适用。本轮待确认的三项已逐项得到用户确认，原始记录见 [内容去重与只读决定](decisions/0003-content-dedup-readonly.md)。

| 编号 | 已确认行为 | 实施影响 |
| --- | --- | --- |
| C07 | 只对后续新接收文件合并；旧归档不批量整理，校验后可供新文件复用。 | 元数据迁移不移动、删除或合并已有实体；历史基线不参与去重。 |
| C08 | 同账号内相同内容合并，包括名称及扩展名不同。 | 实体保留当前名称、位置；来源分别保存原名。后续验证真实打开兼容性。 |
| C09 | 只读默认开启，开关影响以后新建实体；复用旧实体保留其权限。 | 设置与实体实际权限分开；已有实体只能显式应用，不能因新来源而被暗改。 |

M3 交付流式内容校验、实体与多来源模型、新接收文件去重、只读策略及命令入口、外部变化检测、操作恢复和数据库迁移。保留 M2 的多账号隔离、目录归属、暂停和移除语义。

本阶段不做历史实体批量合并、跨账号去重、跨文件系统保存、图形设置、编辑副本、文件编辑或版本管理。M4 的手动重新定位、旧来源恢复入口和长期保留期限不在 M3 实现。

M3 必须先具备多来源失联记录和一致的链接清理：共享实体消失时不能沿用 M2 逐条删除活动记录、丢弃来源关系的实现。仅把这部分最小数据保留前移到 M3；手动恢复流程仍留在 M4。M4 完成前不把去重版本声明为可日常依赖的版本。

## 当前代码需要改变的边界

| M2 现状 | M3 调整 |
| --- | --- |
| `Transfer` 同时保存源、目标与实体身份，默认一源一目标。 | 实体拥有身份、位置、摘要和实际权限；来源独立拥有路径、原名、接收快照与关联状态。 |
| `SyncState` 是按账号保存的基线与 transfers 快照。 | 基线继续隔离；新存储分别限定账号、实体、来源和操作，不能用缺少成员的快照误删共享关系。 |
| 新文件稳定后直接规划移动。 | 稳定后校验内容，先查同账号实体，再选择新建或接入已有实体。 |
| planned 主要覆盖移动与建立链接。 | 操作类型区分新建实体、接入重复来源、权限变更与旧操作恢复，并记录不可逆清理前的恢复信息。 |
| 每条来源独立寻找改名后的实体。 | 先按实体核对一次位置，再逐条处理其来源；共享一轮管理根目录索引。 |
| 失联后移除对应链接与活动记录。 | 共享实体失联时逐来源核对链接、保留记录；不删除源路径的新文件或用户改写的链接。 |
| 只保存文件 mode，不提供保护策略。 | 增加按账号的新实体默认策略，以及实体权限操作记录；不把配置值当成实际保护结果。 |

保留现有排他移动、链接切换、目录身份、账号限定写入、进程锁和书签恢复能力。M2 已修复的重名改址、旧计划重复恢复、未完成账号移除及链接安装后中断场景，都要在新模型上继续验证。

## 数据模型建议

建议升级到 SQLite `user_version = 3`，继续使用系统 SQLite 与单写入连接。逻辑关系如下，具体字段在实现时细化。

```text
账号
 ├─ 历史基线
 ├─ 只读默认设置
 └─ 实体 A ── 微信来源 1
           ├─ 微信来源 2
           └─ 微信来源 3
操作日志记录实体、来源和权限变更的进行阶段
```

| 对象 | 关键内容与约束 |
| --- | --- |
| `entities` | 稳定 UUID、account_id、根目录相对位置、文件身份、尺寸、当前摘要及其校验快照、可访问/待校验/外部变化/失联/冲突状态。 |
| `sources` | 稳定 UUID、account_id、源相对路径、生命周期 ID、原始名称和扩展名、接收时文件身份及可得摘要、entity_id、关联状态。 |
| `content_operations` | 稳定操作 ID、类型、账号/来源/实体 ID、预期两端身份与内容快照、临时路径、阶段、清理与回滚所需信息。 |
| `account_settings` | 每账号的新建实体只读默认值，初始为开启；暂停开关、授权与此设置分开保存。 |
| 权限操作数据 | 实体身份、操作前模式、预期操作后模式、本工具移除的写位及结果；可嵌入操作日志，不重复保存文件内容。 |

来源到实体使用包含 `account_id` 的复合关联约束，确保 A 的来源不能关联 B 的实体。SQLite 支持复合外键，实施时需显式启用并建立满足要求的父键，见 [SQLite 外键文档](https://www.sqlite.org/foreignkeys.html)。按 `(account_id, size, sha256)` 建候选索引，但**不把摘要作为实体唯一主键**：已有重复副本保留、外部修改以及待处理异常都可能产生多个候选。

源路径不是永久来源 ID。同一微信路径被清理、又出现新普通文件时，结束旧来源生命周期，新增来源，不覆盖旧记录。仅对同一账号同一路径的当前生命周期施加唯一约束。实体、来源和历史记录不使用级联删除；来源数从实际关系核对，不能只依赖引用计数决定删除。

接收时摘要与实体当前摘要分开。用户编辑内容后，不能把所有旧来源的“收到的内容”改写成编辑版。迁移记录中没有的数据保持未知，不虚构接收时间、发送者或聊天来源。

## 内容识别与候选选择

推荐采用尺寸筛选、流式 SHA-256，再在合并前逐块比较两端内容。系统 CryptoKit 的 SHA256 支持分块更新与最终摘要，不必一次载入整个文件，见 [Apple SHA256 文档](https://developer.apple.com/documentation/cryptokit/sha256)。摘要用于缩小候选集合，不能仅凭名称、尺寸、inode 或缓存摘要就删除重复内容。

候选只来自同账号已登记的实体，包括经校验的 M2 旧归档。不扫描整个管理根目录并把任意同内容用户文件接管成实体，也不读取启用前的微信历史基线。实体即使已移到另一账号文件夹，所属去重范围仍为原账号。

多份旧副本同时符合时，以已有且验证有效的实体为候选，按已知入库顺序及稳定 ID 决定选择；缺少旧入库时间时使用稳定顺序，不推测微信接收先后。不会为追求“首次名称”改名用户已经整理过的文件。新内容没有候选时，沿用原账号归档目录和同名避让规则。

内容读取与不可逆清理都需核对：

1. 通过不跟随链接的文件打开与描述符检查，确认普通文件身份、尺寸、修改时间及必要的变化信息。
2. 分块读取；结束时再次核对快照。源或实体发生变化则撤销本次判断，重新观察或报告，不使用半成品摘要。
3. 命中缓存的目标在实际复用前仍要重新读取并核对；不能因其曾经只读而跳过验证。
4. 逐块内容比较通过后，在链接切换和冗余内容移除前复核路径仍指向预期对象。

主数据流相同不代表所有元数据可任意丢弃。实施时要检查资源叉、扩展属性、隔离属性、可执行权限及 ACL 的兼容性；不能安全保留的特殊文件留在原处并报告待处理，不直接移除其内容。不得因复用旧实体而降低其隔离属性。首版不承诺处理所有特殊元数据组合。

仍保留稳定观察窗口。只读不是文件锁，也不能证明下载完成；对原有打开句柄的后续写入和任意并发外部修改，不宣称具备不可变快照保证。测试需覆盖观察、摘要、比较和清理前各阶段的变化。

## 新建实体与接入重复来源

### 没有可复用实体

持久化新建实体和来源计划，保留源内容快照及目标；排他移动后，按账号当时的默认策略处理新实体权限，核对身份与内容，再安装原微信路径的链接并提交关联。权限失败不能记成只读成功，操作保留可恢复状态；其他文件与账号仍可处理。

操作一旦持久化，采用记录中的策略完成恢复，不因重启后设置变化而无记录地改变中途行为。配置改变只影响之后新规划的新建实体。原有临时链接、目标重名重试、文件移动后被用户改名等恢复能力必须保留。

### 找到可复用实体

重复来源涉及冗余文件的实际移除，建议采用可核对的交换过程，避免先删除源文件再建立链接。

| 阶段 | 持久化与文件行为 | 中断后的基本恢复依据 |
| --- | --- | --- |
| D0 内容核对 | 两端仍是普通文件，尺寸、摘要和逐块比较一致。 | 未记录操作前不改变文件。 |
| D1 记录接入计划 | 记录来源、实体、两端快照及唯一临时名。 | 重新验证当前两端，不能只信旧摘要。 |
| D2 安装来源链接 | 创建指向实体的临时链接，使用可验证的原子交换使源路径成为链接，原源内容暂存于该操作的临时路径。 | 临时文件保存冗余内容；按身份判断交换是否发生，不重复交换未知对象。 |
| D3 提交关联 | 再次核对实体与临时内容，事务提交来源关联与 `cleanup_pending`。 | 数据库失败时保留临时内容；有计划的文件变化可继续核对。 |
| D4 清理冗余内容 | 确认实体仍包含相同内容、源链接仍属于本操作、临时文件身份匹配后，才移除临时文件。 | 若实体已经丢失或内容变化，保留临时文件并尝试安全回滚，不盲删。 |
| D5 完成 | 清理成功后标记操作完成。 | 清理后提交失败，可通过临时文件已消失及两端状态幂等完成。 |

回滚也须先记录意图，并只交换仍属于本操作的链接和文件。源路径出现其他文件、临时名被占用或身份不符时，保留内容、报告冲突；不覆盖用户对象。不能把数据库事务失败当成文件系统已经自动回滚。

临时内容是未完成操作的工作文件，不是隐藏原件库；正常完成后清理。失败时需要在诊断中列出操作、位置与原因，恢复后按同一规则清理，不能无记录地永久堆积或按文件名前缀批量删除。账号被移除后不再访问其源目录，保留操作记录，显式恢复并重新授权后再继续。

若原实体在冗余清理完成后被用户删除，属于共享文件删除的影响范围；不以隐藏副本维持旧微信入口，也不承诺从记录恢复文件字节。

## 只读策略与外部变化

建议只读策略按账号设置，默认开启，M3 先提供命令行，完整界面留给 M5。写入命令仍要求先停止后台。C09 区分如下：

| 情况 | 建议执行结果 |
| --- | --- |
| 开启后创建新实体 | 移除普通权限中的写位，记录操作与实际结果。 |
| 开启后接入已有可写实体 | 保留可写权限；新来源的状态展示该实体实际可写。 |
| 关闭后创建新实体 | 保留接收文件原有权限，不主动增加写权限。 |
| 关闭后接入已有只读实体 | 保留只读权限，不自动解锁旧文件。 |
| 对已有实体显式应用 | 单独记录逐实体权限任务、范围和结果，不因设置开关而隐式批改。 |
| 用户手动修改权限 | 记录实际状态，不每轮强行改回；复用前仍核对内容。 |

权限通过经过身份核对的实体描述符操作，不对源符号链接路径直接 chmod，也不使用固定 `0444` 覆盖所有模式。只移除必要写位，保留其他必要权限；不自动设置不可变标记或修改 ACL。复杂 ACL 等无法安全支持的情形应报告，不能把普通写位变化等同于所有访问方式都已被禁止。

显式关闭已有实体的保护时，只考虑恢复本工具曾移除的写位。身份不符、原权限未知或模式已有外部变化时不强制恢复；原本就只读的文件不因此变为可写。权限任务也必须覆盖 chmod 成功、状态提交前中断的恢复，避免重复变更破坏用户权限。

外部变化处理建议沿用 M2 的保守边界：

- 同一已知实体身份的内容发生变化：失效旧摘要、等待稳定后重算，记录其当前内容与原接收快照的差别，不覆盖编辑。新来源仅可在完整复核当前内容后关联。
- 目标被另一身份的文件原子替换：先在管理范围查找原实体；找不到时保留两端现场并标记冲突，暂不接管替换文件参与去重。人工确认与重新绑定留待 M4。
- 权限异常、摘要读取失败或文件仍在变化：当前操作等待或报错，不删除内容，不阻塞其他可处理文件。数据库保存失败仍停止共享写入流程。

这些是实施建议，不扩大为“所有软件只能另存”。不新增创建可编辑副本、编辑器或版本管理功能。

## 多来源维护与 M4 边界

实体改名、移入任意管理范围子目录时，先定位实体身份，再更新所有仍由本工具持有的微信链接。每个来源单独记录更新结果；一次失败不意味着其他来源可以覆盖未知对象，也不把“部分来源已更新”记为全部成功。

单个微信来源被清理只结束该来源的关联状态，不删除实体，也不影响其他来源。即使来源数为零，也不通过引用计数自动删除归档实体。

根目录或枚举不可用时保留状态并报告，不能把访问错误标为全部文件已失联。确认本轮完整查找仍无实体时，标记失联并记录各来源；只移除仍指向本工具旧目标的链接。源位置已被其他文件或链接占用则保留并报告。

失联内容再次被收到时，建议创建正常的新实体和新来源，不因为旧摘要记录永久跳过，也不自动批量恢复旧来源。此规则作为 M3 的保守实施建议；M4 再确定旧来源复用、重新定位和保留期限。M3 不提供手动恢复入口，不清除这些恢复所需记录。

## SQLite v2 到 v3 迁移

1. 停止后台并取得现有写入锁；只读命令不触发迁移。校验旧库，沿用 [SQLite Backup API](https://www.sqlite.org/backup.html) 生成私有的一致 v2 备份，不直接复制运行中的单个数据库文件。
2. 在一个事务中保留根目录、账号 UUID、暂停/移除状态、书签、历史基线和账号配置操作，创建实体、来源及内容操作结构。
3. 对 linked 记录建立实体和来源。只在同账号、相同目标位置与身份等证据一致时共享同一迁移实体，不按摘要或名称批量合并旧文件。
4. 将 planned 的目标、临时名、快照与阶段转入兼容恢复操作；conflict 原样保留冲突证据。不得把它们伪装成已完成的新实体，也不能因迁移丢掉已移动的文件。
5. 旧实体摘要为待校验、原权限未知时如实记录，默认策略设为“未来新建只读”；不扫描或 chmod 旧文件，不改写原目标路径或链接。
6. 核对账号隔离、记录数量、关联身份、阶段与外键后提交版本。失败回滚到可读 v2，未知版本与损坏不回退旧 JSON。
7. 授权有效后先恢复旧在途任务，再逐步校验受管理旧实体供新文件复用；暂停和移除规则保持。没有授权的账号不读取实体内容或擅自恢复书签。

迁移事务本身不做文件移动、权限变更或内容删除。旧 JSON / v1 的链式升级逐阶段处理；若 v1 到 v2 已成功而 v2 到 v3 失败，保留有效 v2，不声称整条链自动退回 v1。所有备份只是各自升级前快照，不能覆盖使用中的最新状态。

## 调度、资源与候选缓存

沿用单进程、单写入通道，第一版不增加多个同时移动、交换或清理文件的执行者。内容读取分块、有界内存；建议给摘要任务分配每轮工作预算，避免一个大文件长期占住所有账号。

跨轮任务必须正确持有并释放访问租约；尚未持久化接纳的候选在暂停或授权失效时取消，持久化的在途操作按既有规则恢复。摘要计算内部状态先只保留在内存，重启可重算；未完成摘要不进入有效索引。

复用 M2 的同轮惰性根目录身份索引，程序自身的移动增量登记。内容缓存按账号与实体快照隔离，变化时失效；新候选复用前完整校验。不会每两秒重算所有归档内容，也不会因为新建某个账号而哈希其他账号或任意用户文件。

## 命令建议与文档交付

以下命令已接入，完整操作及限制见用户指南：

| 建议入口 | 用途与边界 |
| --- | --- |
| `--set-read-only ID on\|off` | 修改该账号未来新建实体的默认策略，停止后台后执行。 |
| `--apply-read-only ID on\|off` | 显式应用到已有已登记实体；范围、逐项结果与无法恢复权限的冲突必须可见。 |

| `--recover-operations [ID]` | 停止后台并持锁后，在授权范围内恢复已记录操作；不提供按前缀盲删临时文件的入口。 |

现有账号命令和 `--check` 保持明确职责。后台继续自动恢复有效在途操作；用户诊断不能只显示“进程存活”。实体当前可写、配置默认只读、摘要待校验等状态要分清。命令最终参数可以细化，不能为了开发测试增加可绕过真实目录授权的生产开关。

| B12 | 共享实体改名、跨账号文件夹移动及旧名复用 | 更新原账号的全部有效链接，归属不变，不接管旧名新内容；更新中断可恢复。 |

| B14 | 共享实体移出范围或删除 | 保留实体/来源失联记录，仅清理仍属于本工具的链接；其他源对象保持。 |
| B15 | 失联后再次接收相同内容 | 新文件能正常保存，不永久屏蔽或自动覆盖旧来源记录。 |

| B17 | 开启后复用可写旧实体、关闭后复用只读旧实体 | 权限均保持，配置值与实际结果分开，符合 C09。 |
| B18 | 显式应用已有文件、原本只读、模式外部变化 | 仅更改许可的写位，不覆盖其他权限；未知原模式和身份冲突不强制解锁。 |
| B19 | 权限修改前后中断或提交失败 | 逐实体任务可核对、幂等恢复，不因重试添加本不存在的权限。 |
| B20 | 手动解锁、同 inode 编辑、原子替换 | 旧摘要失效；不把编辑版当原接收内容，不自动接管未知替换文件。 |
| B21 | 资源叉、扩展属性、隔离属性和 ACL 样本 | 支持范围明确，不能安全处理时保留源并报告，不通过去重丢弃附加数据或降低隔离。 |
| B22 | v2 linked/planned/conflict、暂停/移除及未完成账号配置迁移 | 状态、路径、基线、授权与恢复证据保持；旧实体无自动只读或批量合并。 |
| B23 | 备份失败、迁移失败、未知版本与损坏 | 原有效状态保留，不回退 JSON；重复迁移不重放来源或授权。 |
| B24 | 暂停、恢复及移除发生在摘要任务或持久化操作期间 | 新候选停止，在途按规则恢复；已移除账号不再访问源，重新授权后才恢复。 |
| B25 | 批量来源、共享索引、大文件工作预算 | 按实体复用身份查找，缓存按账号隔离；不过量占用内存，不重复计算未变化内容。 |
| B26 | 命令错误、后台持锁及只读诊断 | 未知参数不进入后台，修改持锁互斥，查询不产生隐含文件操作。 |

所有文件、元数据、假账号、书签与数据库均由测试创建于随机临时目录，含用于越界测试的“外部”样本。故障由接口、文件替身和 SQLite 触发器注入。权限测试必须检查实际可写结果与记录，不能只检查设置值；特殊元数据不能创建时如实记录未覆盖，不伪造通过。

不扫描真实微信目录，不读取或迁移本机真实应用状态，不调用真实配置、诊断、后台循环或登录项。安装测试继续使用假 HOME、假应用及命令替身。真实微信的多扩展名打开、只读编辑器提示、暂停续传与沙盒权限在 M6 经单独授权后验收；当前计划不执行这些操作。

## 本轮实现说明

应用入口已使用 `ContentRepository` 和 `ContentCoordinator`。实体、来源、内容日志与权限核心落在独立模块；v2 的 `transfers` 保留作旧 planned 与新建实体移动的兼容日志，`LegacyTransferStore` 每次限定一条操作。未直接重写已有移动状态机，避免丢掉 M1/M2 中断恢复规则。

新增 `content_issues` 保存尚未接纳文件的内容、权限及元数据错误；来源交换、清理、权限操作仍分别保留恢复计划。摘要采用系统 CryptoKit、64 KiB 分块，观察摘要默认每账号每轮 4 MiB，同时最多一个跨轮任务。候选复用前和临时内容清理前的最终核对仍按单文件完整执行，大文件可能延长轮次；本轮不承诺严格跨账号时间片抢占。

附加属性在合并前要求一致，资源叉、隔离属性等样本已纳入临时测试；属性数据校验总量限制为 64 KiB，超出时保留源并报告。带扩展 ACL、不可变标记、其他硬链接的文件不自动修改共享权限或合并。普通新建移动会保留原文件的附加数据，不把数据流摘要视为所有元数据均相同。

M3 已先建立共享实体失联与来源保留，没有加入 M4 手动恢复或历史批量去重。实际测试数、架构自测、限制及测试隔离见 [验收记录](validation-report.md)。本轮未操作真实微信文件、真实应用状态或登录项；按用户指令复核后提交推送。

提交前复核补齐链接目标的持久化历史、准备链接与清理后改名恢复、回滚自身中断、失联清理重试、清理与 chmod 的目录范围复核、反向权限请求以及迁移冲突保持。新加入专项回归的实际结果见验收记录。
